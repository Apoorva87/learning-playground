Read the same cache two ways

A new query changes the mixture of values, even when the cache stays fixed. In a two-position toy row, changing the query from 1 to 0 changes the attention output from 8 to 6.

The scaled score is q·kᵢ/√d. Softmax turns these scores into weights that sum to one. Attention returns the sum of each weight times its value.

Take d = 1, keys 0 and ln(3), and values 2 and 10. For q = 1, exponentiating the scores gives 1 and 3. The weights are ¼ and ¾, and the weighted sum is ¼ × 2 + ¾ × 10 = 8. For q = 0, each exponent is 1 and the answer is (2 + 10)/2 = 6. A real decoder includes the current position among those it can attend to.

This is how different queries read the What can the next token reuse?. It also explains how Share keys and values across heads can share stored values while producing different answers. Transformer, §3.2

What can the next token reuse?

A causal decoder saves a key and a value for each past position at each attention layer. Appending a token cannot change what an earlier position could see, so its old projections remain valid.

Suppose the prompt says “The spare key is in the blue drawer. Open the …”. Prefill processes the prompt and stores its projections. During decode the new position computes its own query, key, and value. It appends its key and value and uses its query to score the eligible keys. The key determines how relevant a position is to this query. The value supplies what it contributes. Each new query needs fresh scores.

Follow Read the same cache two ways to see the same cache return two different answers, then Count a dense KV cache to count what gets stored. Transformer attention

Compress older positions

DeepSeek‑V4‑Flash combines a detailed recent window with compressed global history. Forming summaries reduces the inventory of stored entries. Sparse selection reduces how many entries a query reads.

Compressed Sparse Attention (CSA) produces finer summaries and selects relevant ones for each query. Heavily Compressed Attention (HCA) uses coarser summaries and can read all of them. A model can therefore store many entries yet consult only a few on a particular step. Grouping positions also changes the detail represented by each entry.

V4.1‑Flash adds sharing across layers through Let several layers read one global store. Check the distinction between stored and selected entries in Predict what changes. DeepSeek‑V4‑Flash model card

Count a dense KV cache

One token in the example MHA model adds 512 KiB. At 4,096 tokens the cache holds 2 GiB for one sequence. A dense decoding step still reads keys and values from the history.

Multiply batch × tokens × layers × KV heads × head dimension × 2 arrays × bytes per number. Here one token costs 1 × 32 layers × 32 heads × 128 numbers × 2 arrays × 2 bytes = 524,288 bytes. At 8,192 tokens the total reaches 4 GiB. This counts the ideal KV tensors. Weights, temporary storage, and allocator overhead have separate budgets.

Try Share keys and values across heads to change just one factor. Use Reconstruct 890 bytes per token for an architecture with a different storage layout. Fast Transformer Decoding

Price one compressed entry

A V4.1‑Flash global entry has a 288-byte main vector and a 68-byte index key. Count the scale bytes as well as the packed four-bit values.

For the 512-channel main vector, two four-bit values occupy one byte and each group of 16 channels shares one scale byte. The total is 512/2 + 512/16 = 288 bytes. For the 128-channel index key, groups of 32 share a scale byte, giving 128/2 + 128/32 = 68 bytes. The combined price is 356 bytes. The local sliding-window cache uses FP8.

Multiply this price by the global writer rate from Let several layers read one global store to get the Reconstruct 890 bytes per token. DeepSeek‑V4.1‑Flash precision · Reference implementation

Reconstruct 890 bytes per token

DeepSeek reports 890 bytes of global KV per token for V4.1‑Flash. That is about one quarter of V4‑Flash’s corresponding global footprint at equal context length.

The two ingredients are Price one compressed entry (288 + 68 = 356 bytes per global entry) and Let several layers read one global store (3 × ½ + 1 = 2.5 entries per token). Multiply them: 356 × 2.5 = 890 bytes per token. At exactly one million tokens this term is 890,000,000 bytes, or 890 decimal MB (about 849 MiB). The local window, weights, allocator overhead, and temporary activations consume additional memory. The reported one-eighth figure concerns persistent storage in a different comparison.

Return to Count a dense KV cache to compare what each formula counts before using the numbers. Technical report · Release announcement

Store a learned latent

DeepSeek‑V2’s multi-head latent attention stores a compact learned vector per position plus a positional key. Head-specific projections can use that shared vector.

Let c = W↓h compress the token’s hidden state h. The content score qᵀ(W↑c) equals (W↑ᵀq)ᵀc. Moving the projection onto the query allows scoring directly against the stored latent. The positional key preserves rotary position information. This reduces how many numbers each position needs while retaining head-specific transformations.

Compare this representation with the explicit KV banks in Share keys and values across heads. Another dimension available for compression is the number of positions represented, explored in Compress older positions. DeepSeek‑V2, §2.1

Share keys and values across heads

Keep 32 query heads. With 8 KV heads, each group of four queries reads one KV bank. With one KV head, every query reads the same bank. Each query still computes its own attention weights.

In the Count a dense KV cache example, MHA (32 KV heads), GQA (8), and MQA (1) use 2 GiB, 512 MiB, and 64 MiB respectively at 4,096 tokens. At 8,192 tokens they use 4 GiB, 1 GiB, and 128 MiB. These are hypothetical architectures with equal layer count, head size, and precision. An existing MHA model would need training or adaptation to share heads this way.

Historically, MQA appeared in 2019 and GQA in 2023. A different way to share information across heads is Store a learned latent. MQA paper · GQA paper

Let several layers read one global store

In DeepSeek‑V4.1‑Flash, a Full layer writes global KV and selects positions. A Reindex layer reads shared KV and chooses new positions. A Reuse layer also reuses a preceding selection.

Every layer computes its own attention query and retains its own 128-token local attention window. Of the global writers, three encoder layers each write one entry per pair of tokens; one decoder layer writes one entry per token. Averaged over a long sequence that is 3 × ½ + 1 = 2.5 entries per token across the network. A fractional average counts entries over many tokens.

Combine that rate with Price one compressed entry to reconstruct the Reconstruct 890 bytes per token. Earlier Compress older positions addresses how far back positions are represented. CSA2 and model configuration, §§2.3 and 4.2.1

Predict what changes

Start with 4,096 tokens and 8 KV heads in the toy model. Double the sequence length and halve the number of KV heads. Predict the memory cost before opening the linked explanation.

Check: in Count a dense KV cache, the factors of 2 and ½ cancel. The result stays at 512 MiB. All 32 query heads still have a KV group to read. Now compare two designs that each read 512 global entries per query. If one stores a same-sized entry per token and the other stores one per four tokens, which cache grows faster?

Check: the first stores about four times as many entries over a long prefix. A read limit is insufficient to determine storage. Revisit Compress older positions for the mechanism, then try explaining Reconstruct 890 bytes per token without looking up its two factors.
