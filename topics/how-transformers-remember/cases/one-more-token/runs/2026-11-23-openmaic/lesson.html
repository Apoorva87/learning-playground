Predict one more token

Suppose the prompt says “The spare key is in the blue drawer. Open the …”. During prefill, a causal transformer processes the prompt and, at each attention layer, saves a key and a value for every position. A key describes what might make that position relevant. A value carries what the position can contribute if selected. Think of an entry in an index and the passage the entry points to. In the model, both are learned vectors, so a position can match a question by degrees.

During decode, the newest position makes a fresh query. It scores the cached keys, turns those scores into weights, and blends the corresponding values. The model also computes and appends the new position’s key and value. Why is reuse valid? Causal attention prevents a later word from changing the hidden state at an earlier position. With the same prefix, weights, positions and inference settings, those earlier projections can be reused. The newest query still reads the history in dense attention, so adding a token to a long prompt involves more memory traffic than adding one to a short prompt. Do one attention calculation by hand

For a single head, let q be the new query, kᵢ and vᵢ the key and value at position i, and d the key dimension. The score is sᵢ = q·kᵢ / √d. Convert scores to weights with aᵢ = exp(sᵢ) / Σⱼ exp(sⱼ). The output is Σᵢ aᵢvᵢ. Later layers use that result when predicting a token.

Try an attention row with two eligible positions. Set d = 1, q = 1, keys to 0 and ln(3), and values to 2 and 10. Exponentiating the two scores gives 1 and 3, so the weights are ¼ and ¾. The output is ¼ × 2 + ¾ × 10 = 8. A different query changes those weights even when it reads the exact same cache. For q = 0, both weights become ½ and the output becomes 6. A real decoder also admits its current position to the attention row. Transformer attention, §3.2

Count the bytes

For dense attention with equal key and value dimensions, ideal tensor storage is

bytes = batch × tokens × layers × KV heads × head dimension × 2 arrays × bytes per element.

With one sequence, 32 layers, 32 KV heads, head dimension 128, and 2-byte elements, one new token adds 32 × 32 × 128 × 2 × 2 = 524,288 bytes, or 512 KiB. At 4,096 tokens that is 2 GiB. This toy model lets us change a single variable at a time.

The route from separate heads to shared history

2017–2023 · Share across heads. The original Transformer assigns different projections to attention heads. MQA gives all query heads one set of keys and values. GQA splits the query heads into groups, providing one KV set per group. This reduces stored bytes and the amount of KV data that must move during decode. Query heads can still attend to different positions. Transformer · MQA · GQA

2024 · Store a learned latent. DeepSeek‑V2’s multi-head latent attention (MLA) compresses the hidden state h into a compact vector c = W↓h. Heads learn different projections of c. In the content part of an attention score, qᵀ(W↑c) = (W↑ᵀq)ᵀc. That identity lets an implementation score cached latents directly. A small positional key is cached separately for rotary position information. A latent costs fewer numbers per position while still supporting different heads. DeepSeek‑V2, §2.1

2026 · Compress along the sequence. V4‑Flash keeps a detailed recent window and represents older context with learned summary entries. Compressed Sparse Attention (CSA) forms summaries at a finer stride and chooses relevant ones for a query. Heavily Compressed Attention (HCA) forms much coarser summaries and can attend to all of them. Two costs are at play. Packing more tokens into each entry reduces how much history is stored. Selecting fewer stored entries reduces the work of reading them for the next token. DeepSeek‑V4 model card and technical report

2026 · Share across layers and shrink each entry. DeepSeek‑V4.1‑Flash uses CSA2. A Full layer writes a global cache and selects positions. A Reindex layer reads that cache and picks positions for its own query. A Reuse layer reads the cache and a preceding layer’s selection. Each layer still computes its own attention query and keeps its local 128-token window. The encoder’s global entries cover pairs of positions. The decoder’s cover single positions, with many layers reading the same store. DeepSeek‑V4.1‑Flash, §§2.3 and 4.2.1

Follow the rounding. The main global cache uses 4-bit numbers with a one-byte scale per group of 16. Sixteen such values cost 8 + 1 = 9 bytes. Storing 16 BF16 values takes 32 bytes. That small example explains one ingredient. The model’s overall cache also includes the indexer and benefits from sharing entries across layers. Its local sliding-window cache uses FP8. DeepSeek‑V4.1‑Flash, §2.4.4

What fits in 890 MB?

Here is one way to reconstruct the reported global total from the released configuration. A 512-channel main entry takes 512/2 bytes of FP4 payload plus 512/16 scale bytes, or 288 bytes. Its 128-channel index key takes 128/2 payload bytes plus 128/32 scale bytes, or 68 bytes. Together they cost 356 bytes per entry. Three encoder cache writers each create one entry per two tokens. One decoder writer creates one per token. Over a long sequence, the average is (3 × ½ + 1) × 356 = 890 bytes per token across the network. The other layers can use those entries again. Model configuration and inference code · Released architecture and dimensions, §4.2.1

DeepSeek reports 890 bytes of global KV cache per token, about one quarter of V4‑Flash’s corresponding footprint. At exactly 1,000,000 tokens that is 890 MB, about 849 MiB. Weights, the bounded local window, temporary activations, and allocator overhead require additional memory. For persistent storage on SSD or host memory, DeepSeek reports about one eighth of its predecessor’s footprint, aided by reconstructing missing sliding-window state when a session resumes. These ratios have different denominators. DeepSeek technical report, §§2–3 · Release announcement

Explain it back. Two designs both read 512 global entries per query. One stores an entry for every old token and one stores an entry per group of four. Would their long-context caches occupy the same memory? With equal entry sizes and all else fixed, the second stores about a quarter as many entries. The read limit alone tells you little about the total inventory.

Test yourself

Choose an answer to each OpenMAIC question, then open its explanation.

1. Consider a cache with keys and values that produce scores of 0 and ln(3) for a specific query, resulting in softmax weights of 1/4 and 3/4 respectively. If the associated values are 2 and 10, what is the attention output for this query? Contrast this with the result if the query were zeroed out.

Show explanation

For the specific query, the result is calculated as the weighted sum of values: (1/4 * 2) + (3/4 * 10) = 0.5 + 7.5 = 8. For a zeroed query, the scores are all equal (typically resulting in uniform weights), so the output is the average of the values: (2 + 10) / 2 = 6. This demonstrates that a fresh query can yield different results even with identical cached keys and values.

2. In the DeepSeek-V2 MLA architecture, how does the storage mechanism for attention heads differ from Grouped Query Attention (GQA)?

Show explanation

DeepSeek-V2 MLA introduces a shared compact learned latent and a positional key. Head-specific projections map to this latent, which is distinct from GQA where groups of query heads share one explicit KV pair. This design allows for efficient compression while maintaining head-specific capabilities.

3. In the DeepSeek V4.1-Flash CSA2 architecture, how does the system handle token processing across layers compared to simply shrinking storage?

Show explanation

DeepSeek V4.1-Flash CSA2 shares a global store across layers. Reindex chooses new positions in this store, and Reuse allows sharing the store with preceding selection. Crucially, each layer still maintains its own query and a local 128-token window. This setup involves sparse reading of entries rather than just shrinking storage.

4. Calculate the global cache footprint per token for a DeepSeek V4.1-Flash system where one main entry costs 288 bytes and index costs 68 bytes. Assume three encoder writers create one entry per two tokens, and one decoder writer creates one entry per token.

Show explanation

The total cost per entry is 288 + 68 = 356 bytes. The writer rate is (3/2) from encoders plus 1 from the decoder, totaling 2.5 global entries per token. Therefore, the cost per token is 2.5 * 356 = 890 bytes. This calculation accounts for global entries and indices; local sliding-window states, weights, and workspace are additional costs not included in this specific figure.
