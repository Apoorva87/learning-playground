Why keep both kinds of block?

Consider the word “keys” in the saved prompt. When a later token needs it, the two mixers have different ways to find what matters.

Recurrent memory

Each head holds a matrix of associations. The current key looks up what the matrix would predict, then the block writes a correction toward the new value. Later queries read the updated matrix. Several tokens can change the same association, so a particular old token has no dedicated slot to revisit.

Full attention

Every position keeps its own key and value. A new query compares with all visible keys and can assign a large weight to one old position. This preserves a path to individual tokens, while the storage and score calculations grow with the prefix.

Watch a query read the cache

The hybrid puts a position-by-position lookup in every fourth block. The other 48 avoid a growing KV history. With fixed head sizes, the recurrent work per new token stays bounded as the prefix grows. A full-attention decode scores a number of keys proportional to prefix length. During prefill its full score grid grows quadratically with prompt length. The recurrent prefill uses a chunked computation of its update. These are architecture costs. The actual speed also depends on the kernels and hardware. See the timings of this CPU run.

Work through the bytes

One full-attention block stores 2 tensors × 4 KV heads × 256 features × 2 BF16 bytes = 4 KiB per position. Sixteen blocks add 64 KiB per token. An all-GQA stack with the same head sizes would add 256 KiB per token.

One recurrent block stores 48 × 128 × 128 FP32 elements (3 MiB), plus 10,240 × 4 BF16 convolution elements (80 KiB). Across 48 blocks that is 147.75 MiB fixed. Equal retained bytes occur at 788 positions. Above that length the hybrid uses less cache under these assumptions. The recorded experiment covers 16 and 17 positions.
