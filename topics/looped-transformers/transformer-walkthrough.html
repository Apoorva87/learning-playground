One sentence through a modern transformer

Article C · the plain machinery with real numbers · then Article A (looping) and Article B (a real looped model)

We follow one small sentence, “The capital of France is”, through a real model, Qwen3-0.6B-Base, and then let it write one more word. Every vector (the first 16 of its numbers), attention weight and probability in the scene comes from a recorded run, and the small steps are recomputed in code and checked against it. The weight matrices themselves are described by their shapes and counts, not drawn. The model has the features of recent designs: grouped-query attention (GQA), query-key normalisation, rotary positions (RoPE), RMSNorm and a gated feed-forward layer. Near the end, a real model with multi-head latent attention (MLA) shows how the cache can shrink further. Controls work as in the other articles: Scroll, Step or Play, and 🔊 Narrate reads it aloud.

The journey

A language model does one thing: given some text, it scores every possible next token. Writing a sentence is doing that again and again. Here the text is five tokens and the model is 28 identical-looking layers deep, each working on vectors of 1024 numbers. The journey has two passes. Prefill reads the whole prompt at once and builds a memory, the KV cache. Decode then adds one token at a time, reading that memory instead of recomputing it.

The scene shows one decoder layer, the block that repeats. Over the next beats we open it: the normalisation, the attention with its 16 query heads sharing 8 key/value heads, and the gated feed-forward network. Then we leave the stack, turn the last vector into a score for each of the 151,936 tokens in the vocabulary, pick one, and write it down.

An assembly line for meaning. The sentence enters as five separate tokens. Layer after layer, each token's vector absorbs information from the earlier tokens and refines itself, and at the end only the last token's vector is asked to say what comes next.

$$\underbrace{\text{ids}}_{[5]} \;\to\; \underbrace{h_0}_{[5,\,1024]} \;\xrightarrow{\ 28\ \text{layers}\ }\; \underbrace{h_{28}}_{[5,\,1024]} \;\xrightarrow{\ \text{last row, norm, } E^{\top}\ }\; \underbrace{\text{logits}}_{[151936]} \;\to\; \text{token}$$

The model is Qwen3-0.6B-Base. We loaded it in 32-bit floats and recorded layer 0 by hand in 64-bit arithmetic, which matched the model's own output to better than one part in a hundred thousand. Its next-token choice is the whole point of the next hundred paragraphs: it picks one token with probability 34.6%.

Tokens

The model never sees letters. A tokenizer, trained once on text, cuts the sentence into pieces from a fixed vocabulary of 151,936 entries and gives each piece an integer ID. Our sentence becomes five pieces: The (ID 785), capital (6722), of (315), France (9625) and is (374). The space belongs to the token that follows it, so “ capital” and “capital” are different entries. The embedding table has 151,936 rows, of which the tokenizer defines 151,669; the rest are padding.

A vocabulary is a numbered list of word-pieces, like a library catalogue. Common words get their own number, rare words are spelled out from smaller pieces, and the numbers carry no meaning of their own. They are just addresses.

$$\text{ids} = [785,\ 6722,\ 315,\ 9625,\ 374] \in \mathbb{N}^{[5]}$$

Five integers, shape \([5]\). Everything that follows is arithmetic on these five numbers' vectors.

From IDs to vectors

The first real computation is a lookup. The model owns an embedding table \(E\) with one row of 1024 numbers for each of the 151,936 tokens. Token 374 selects row 374, and so on. Stacking the five rows gives \(h_0\), a table of five vectors. Row norms are all below one: ‘ France’ has length 0.881 and ‘ is’ has 0.75. The scene shows the first 16 of each row's 1024 numbers, red for positive and blue for negative, with brightness for size. The first three of ‘ is’ are 0.0183, 0.0234 and -0.0554.

Two things are missing, on purpose. No position is added here: Qwen3 puts position into attention, as we will see in the rotary-position beat. And there is no norm on the embedding. The same table is reused at the end to score tokens, because the model ties its input and output embeddings.

Each token becomes a point in a 1024-dimensional space, and training has pushed points that behave alike close together. At this stage the point only knows which token it is. It knows nothing about its neighbours yet, which is attention's job.

$$h_0 \;=\; E[\text{ids}] \in \mathbb{R}^{[5,\,1024]}, \qquad E \in \mathbb{R}^{[151936,\,1024]}$$

The table holds \(151936 \times 1024 = 155{,}582{,}464\) numbers, about a quarter of the model's 596 million parameters. Looking up a row costs no arithmetic, only memory reads: 5 rows of 1024 numbers.

One layer, from above

Each of the 28 layers has the same shape of work, in two halves. First the tokens exchange information: normalise, attend, and add the result back. Then each token is processed alone: normalise, run a small two-way network, and add the result back. The additions are the residual connections. They mean a layer never replaces a token's vector. It only adds corrections to it, so the same vector travels the whole stack.

The code adds the attention result to the input and then adds the feed-forward result. Both sublayers read a normalised copy, and the residual carries the original.

A shared notebook passed down 28 desks. Each desk reads it, jots a correction in the margin, and passes it on without erasing anything. By the end the notebook holds the sum of everyone's notes.

$$h' = h + \operatorname{Attn}\big(\operatorname{RMSNorm}(h)\big), \qquad h'' = h' + \operatorname{FFN}\big(\operatorname{RMSNorm}(h')\big), \qquad h,\,h',\,h'' \in \mathbb{R}^{[5,\,1024]}$$

The shape never changes: five rows of 1024 numbers in, five rows of 1024 out. Per layer, attention holds 6,291,456 weights and the feed-forward network 9,437,184, so 28 layers hold 440 million of the model's 596 million parameters.

RMSNorm, with real numbers

Normalisation gives every matrix multiply an input of a steady scale. It normalises only the copy that each sublayer reads, so the running vector itself keeps growing, as the stack beat shows. Qwen uses RMSNorm. For one token's vector it computes the mean of the squares of its 1024 numbers, takes the square root and divides by it, then multiplies each feature by a learned gain. In the code that is a reciprocal square root of the mean square plus epsilon, followed by a multiplication by a learned weight.

Worked for the last token, ‘ is’: the mean of its squared numbers is 0.0005497, so \(1/\sqrt{\text{mean} + \epsilon}\) is 42.61. Its first number, 0.0183, becomes \(0.0183 \times 42.61 = 0.780\) after rescaling, then \(0.780 \times 0.1377 = 0.1074\) after the learned gain. That is exactly the recorded output. Before the gain the vector has unit root-mean-square, whatever size it came in, and the gain then reshapes it feature by feature.

Setting every token's volume to the same level before it enters a matrix multiply, then letting a per-feature dial (the gain) turn some features up and others down. Unlike LayerNorm, there is no subtracting the mean and no bias: it only rescales.

$$y_i \;=\; \frac{x_i}{\sqrt{\tfrac{1}{1024}\sum_{j=1}^{1024} x_j^{2} + \epsilon}}\; g_i, \qquad x,\,y,\,g \in \mathbb{R}^{1024},\quad \epsilon = 10^{-6}$$

For all five tokens the input and output are \([5,\,1024]\). Cost: one pass over 1024 numbers to square and add, one to scale. It is cheap beside a matrix multiply, but it must read and write the whole activation, so it matters in memory traffic. Each layer applies it twice, and the final norm once more before the head.

Queries, keys and values

Attention starts with three matrix multiplies of the normalised vectors. One makes queries (what this token is looking for), one makes keys (what each token advertises), and one makes values (what it hands over when chosen). The query matrix maps 1024 numbers to 2048, which is 16 heads of 128. The key and value matrices map 1024 numbers to 1024, which is only 8 heads of 128. That asymmetry is grouped-query attention, in the next beat.

For the last token, query head 0 begins -0.0469, 0.136, 0.0572. Each head works only on its own 128-wide slice.

Every token writes a search request (the query), a label (the key) and a package (the value). A token scores its request against everyone's labels, and collects a blend of the packages of the best matches.

$$Q = X_n W_Q \in \mathbb{R}^{[5,\,2048]},\qquad K = X_n W_K \in \mathbb{R}^{[5,\,1024]},\qquad V = X_n W_V \in \mathbb{R}^{[5,\,1024]}$$

The weights are \(W_Q \in \mathbb{R}^{[1024,\,2048]}\) (2,097,152 numbers) and \(W_K, W_V \in \mathbb{R}^{[1024,\,1024]}\) (1,048,576 each). Together the three multiplies cost \(2 \times 5 \times 4{,}194{,}304 \approx 42\) million operations for the five tokens of one layer.

Grouped-query attention

Classic multi-head attention gives every query head its own key and value head. Qwen3-0.6B does not: its 16 query heads are split into 8 pairs, and each pair shares one key head and one value head. The code divides the query heads by the key/value heads to get this group size of 2. Query heads 0 and 1 read key/value head 0, heads 2 and 3 read head 1, and so on.

The model loses a little flexibility. In return the key/value heads are half as many, so everything that has to be stored for each earlier token, the KV cache, is half as big. During generation, reading that cache is a main cost, and this is why most recent models use it. The extremes of the idea are multi-query attention (every query head shares one key/value head) and plain multi-head attention (no sharing); GQA sits between them.

Sixteen readers, eight libraries. Each pair of readers shares one library card, so the library keeps eight shelves instead of sixteen, and the readers can still ask different questions.

$$\operatorname{kv}(h) = \lfloor h / 2 \rfloor, \qquad h = 0,\dots,15; \qquad K_{\text{cache}},\,V_{\text{cache}} \in \mathbb{R}^{[8,\,T,\,128]}$$

Per token and layer the cache holds \(2 \times 8 \times 128 = 2048\) numbers, or 4,096 bytes in BF16. With 16 key/value heads it would be 8,192. We return to this in the cache beats.

Normalising queries and keys

Qwen3 adds a small step that older models lack. After the projections, each query head and each key head is passed through its own RMSNorm over its 128 features, before position is applied. The code does it with a norm on the reshaped queries and the same for keys.

The effect on our numbers is large. For ‘ is’, query head 0 started as -0.0469, 0.136, 0.0572, and after the norm it is -0.864, 0.686, -0.171. The head was multiplied by 4.066 (for ‘ The’, 5.811), and then each feature by its learned gain, whose first three values are 4.53, 1.24 and -0.734. That negative third gain is why the third number changed sign.

A volume limiter on the question and the label before they are compared. Scores are dot products, and dot products grow with the length of their vectors. Fixing the lengths first stops a single head from producing runaway scores. That is the usual reason given for the step, and it is a reading of the design, not something the code states.

$$\hat q = \frac{q}{\sqrt{\tfrac{1}{128}\sum_{j=1}^{128} q_j^{2} + \epsilon}}\odot g_q, \qquad \hat k = \frac{k}{\sqrt{\tfrac{1}{128}\sum_{j=1}^{128} k_j^{2} + \epsilon}}\odot g_k, \qquad q,\,k,\,g_q,\,g_k \in \mathbb{R}^{128}$$

The shapes are unchanged, \([5,\,16,\,128]\) for queries and \([5,\,8,\,128]\) for keys. The norm is applied to each of the 16 query heads and 8 key heads separately, using one shared 128-wide gain per kind.

How the norm moved: post-norm, pre-norm, RMSNorm

The first Transformer normalised after the residual add: the output of each sub-layer is the layer norm of the input plus the sub-layer applied to that input. LayerNorm itself comes from Ba and colleagues (2016), who compute the mean and variance used for normalization from all of the summed inputs to the neurons in a layer. Where the norm sits turned out to matter for training. Xiong and colleagues (2020) analysed the original placement and found that the expected gradients of the parameters near the output layer are large at initialisation, so the warm-up stage is practically helpful. With the norm moved inside the residual branch, the gradients are well-behaved at initialization, and they report that one can remove the warm-up stage for the training of Pre-LN Transformers.

The second change shrank the norm itself. Zhang and Sennrich (2019) proposed RMSNorm, which regularizes the summed inputs to a neuron in one layer according to root mean square (RMS), on the hypothesis that re-centering invariance in LayerNorm is dispensable; they report it is computationally simpler and thus more efficient than LayerNorm. LLaMA (2023) combined both moves. Its authors write that they “normalize the input of each transformer sub-layer, instead of normalizing the output” and “use the RMSNorm normalizing function”. The Qwen3 model in this walkthrough follows the same recipe.

A third norm is newer. Henry and colleagues (2020) proposed QKNorm, a normalization technique that modifies the attention mechanism. Qwen3 applies an RMSNorm to every query head and key head, which is the step in the beat just before this one. Qwen3’s version is a per-head RMSNorm with a learned gain, not the same arithmetic as theirs.

On our model the choice costs almost nothing in arithmetic. At width 1024 a LayerNorm takes about 7,168 operations per vector and holds 2,048 parameters (a gain and a bias). An RMSNorm takes 4,096 operations and holds 1,024. For our five tokens and the two norms in a layer, that is 71,680 operations against 40,960, next to about 157 million operations in the layer’s matrices. So the case for RMSNorm is simplicity and one pass over the data fewer, not arithmetic. None of this touches the KV cache: keys are cached after QK-norm and rotation, at the same 4,096 bytes per token per layer.

Think of the residual stream as a highway that carries the running answer from the first layer to the last. Post-norm puts a toll booth on the highway after every junction, rescaling everything that passes. Pre-norm puts the booth on the on-ramp of each sublayer, so the highway itself is left alone and each junction only adds to it. RMSNorm then makes the booth quicker: it measures only how long the vector is, not where its average sits.

$$\begin{aligned}y_{\text{post}}&=\mathrm{Norm}\big(x+F(x)\big)\\ y_{\text{pre}}&=x+F\big(\mathrm{Norm}(x)\big)\end{aligned}$$

$$\begin{aligned}\mathrm{LN}(x)&=\frac{x-\mu}{\sqrt{\sigma^{2}+\epsilon}}\odot\gamma+\beta\\ \mu&=\tfrac1d\sum_i x_i,\qquad \sigma^{2}=\tfrac1d\sum_i (x_i-\mu)^2\\ \mathrm{RMS}(x)&=\frac{x}{\sqrt{\tfrac1d\sum_i x_i^{2}+\epsilon}}\odot g\end{aligned}$$

Counting one operation per addition or multiplication per element of a \([5,\,1024]\) block: LayerNorm sums to get the mean, subtracts it, squares, sums, scales by the inverse standard deviation, then applies \(\gamma\) and \(\beta\), which is \(7d\). RMSNorm squares, sums, scales and applies \(g\), which is \(4d\). With \(d=1024\) that is 7,168 and 4,096. This tally is ours, not the papers’.

$$\begin{aligned}x_L&=x_0+\sum_{l=0}^{L-1}F_l\big(\mathrm{Norm}(x_l)\big)\\ \frac{\partial x_L}{\partial x_0}&=I+\sum_{l=0}^{L-1}\frac{\partial F_l(\mathrm{Norm}(x_l))}{\partial x_0}\end{aligned}$$

That is the chain-rule picture, a way to see why the placement matters; Xiong and colleagues give the careful analysis. In our model the norms act on vectors of shape \([5,\,1024]\) and are 57 of width 1024 (two per layer and a final one), so RMSNorm holds 58,368 gain parameters where LayerNorm would hold 116,736.

Rotary positions

So far nothing says where in the sentence a token sits. Qwen adds that information by rotating queries and keys. Take the 128 features of a head as 64 pairs, the pair \((x_i,\ x_{i+64})\) for \(i = 0 \ldots 63\) (the code pairs the first half with the second half). Each pair is a point in a plane, and RoPE turns it through an angle equal to the token's position times a frequency that depends on the pair: 1,000,000 to the power \(-2i/128\). Pair 0 spins fastest, at one radian per position. Pair 63 turns at 0.00000124 radians per position, so it barely moves over thousands of tokens.

A worked case. Token ‘ is’ sits at position 4, so pair 0 turns by \(4 \times 1.0 = 4\) radians. Its query pair is \((\)-0.8644, -0.2421\()\), and after the rotation it is 0.3818 and 0.8125. Its length is unchanged. Only its direction moved. Keys are rotated the same way, and it is applied to the normalised queries and keys.

Many clock hands on every token, each turning at its own speed: seconds, minutes, hours and slower. Rotating by position stamps a time on the vector. When a query and a key are later compared, what survives is the difference of their stamps, so the score depends on how far apart two tokens are, not on where the sentence starts.

$$\begin{aligned}\begin{pmatrix} x_i' \\ x_{i+64}' \end{pmatrix} &= \begin{pmatrix} \cos\phi & -\sin\phi \\ \sin\phi & \cos\phi \end{pmatrix}\begin{pmatrix} x_i \\ x_{i+64} \end{pmatrix} \\[6pt] \phi &= p\;\theta^{-2i/128},\qquad \theta = 10^6,\quad p = 0,\dots,4\end{aligned}$$

Queries \([5,\,16,\,128]\) and keys \([5,\,8,\,128]\) are rotated pair by pair. The rotation is applied to each of the 64 pairs of each head, \(x \in \mathbb{R}^{128}\) in, \(x' \in \mathbb{R}^{128}\) out. Check the example: \(-0.8644\cos 4 - (-0.2421)\sin 4 = 0.3818\), the recorded value.

How position got in: add, learn, rotate

Attention alone cannot tell “dog bites man” from “man bites dog”: the scores depend on which tokens are present, not on where they sit. Every design has to put order in somewhere. The original Transformer did it at the input. Its authors write that “we use sine and cosine functions of different frequencies”, added to the embeddings, chosen because it may allow the model to extrapolate to sequence lengths longer than those met in training. The authors also tried learned position embeddings and found that the two versions produced nearly identical results.

Two limits showed up. A learned table has a fixed number of rows, so a position without a row cannot exist, and the table costs parameters: for a 32,768-token context at our width it would hold 33,554,432 of them, about 5.6% of this model’s 596 million. And an added absolute position says where a token is, while attention often needs how far apart two tokens are. Shaw and colleagues (2018) went after that second point by extending the self-attention mechanism to efficiently consider representations of the relative positions.

Rotary embeddings (RoPE) changed where position acts. Su and colleagues (2021) encode the absolute position with a rotation matrix applied to queries and keys, and after rotation the score depends on the offset between the two tokens. LLaMA adds rotary positional embeddings (RoPE) at each layer of the network, and so does Qwen3. ALiBi (Press and colleagues, 2021) drops position vectors altogether: ALiBi does not add positional embeddings to word embeddings; it biases query-key attention scores with a penalty that is proportional to their distance, using a head-specific slope fixed before training.

For our model: sinusoidal and rotary positions add no parameters, a learned table would add 33,554,432. RoPE rotates 16 query heads and 8 key heads of 128 numbers in every layer, about 9,216 operations per token per layer in our tally, three for each number rotated. ALiBi adds one bias per head per cached key, so 524,288 additions per layer on each decode step at a 32,768-token context. The KV cache keeps its size: with RoPE the cache stores keys already rotated for their own position, so they are never rotated again, and with positions added at the input they are already inside the keys and values. MLA keeps a separate 64-number rotated key beside its latent; the MLA beat, later on, shows it with real numbers.

Sinusoidal and learned positions are name tags pinned on each token before the meeting starts. RoPE and ALiBi change the seating instead: two tokens are compared by how far apart they sit. RoPE turns the question and the label by angles proportional to their positions, so the match depends only on the difference. ALiBi simply subtracts a penalty for distance.

$$\begin{aligned}x_{\text{pos}}&=e_{\text{token}}+\mathrm{PE}(\text{pos})\\ \mathrm{PE}(\text{pos},2i)&=\sin\frac{\text{pos}}{10000^{2i/d}}\\ \mathrm{PE}(\text{pos},2i+1)&=\cos\frac{\text{pos}}{10000^{2i/d}}\end{aligned}$$

$$\begin{aligned}\big(R_{m}\,q\big)^{\top}\big(R_{n}\,k\big)&=q^{\top}R_{\,n-m}\,k\\ \theta_i&=\big(10^{6}\big)^{-2i/128}\end{aligned}$$

$$\begin{aligned}s_{ij}&=\frac{q_i\cdot k_j}{\sqrt{d_h}}-m_h\,(i-j)\\ m_h&=2^{-8h/n},\quad h=1,\dots,n\end{aligned}$$

The rotary line is the form Su and colleagues derive: the product of the rotated query and the rotated key equals the query times a single rotation by the offset times the key. Here \(R_m\) turns each pair of features \((x_i,\,x_{i+64})\) by the angle \(m\,\theta_i\). The pairs and the base \(10^6\) are Qwen3’s, as in the rotary beat, and each query head has shape \([5,\,128]\).

Scores, the mask and softmax

Now each token compares its query with every key. The score between token \(t\) and token \(u\) is their dot product, divided by \(\sqrt{128}\) so it stays in a sensible range. The code computes the query times the transposed key, scaled. A token may only look backwards, so every score for a later token is set to minus infinity, the causal mask. Then a softmax over the keys turns each row into weights that are positive and sum to one.

The scene shows head 0 of our layer. The last row, for ‘ is’, has raw scores 8.17 for ‘ The’, 4.57 for ‘ capital’, 8.06 for ‘ of’, 5.3 for ‘ France’ and 7.35 for itself. After the softmax these become 41.2%, 1.13%, 37%, 2.35% and 18.3%. This head puts most of its attention on the first token and on ‘ of’. Other heads do something else: head 5 gives 83.9% to the token itself.

A budget of attention that sums to 100%. Softmax makes the best matches take most of it. Scores 8.17 and 8.06 are close, so those two tokens split the budget; a score of 4.57 is smaller by about 3.6 and gets almost nothing, because softmax works on exponentials. The mask is the rule that no one may read the future.

$$\begin{aligned}s_{t,u} &= \frac{q_t \cdot k_u}{\sqrt{128}} \\ a_{t,u} &= \frac{e^{s_{t,u}}}{\sum_{u' \le t} e^{s_{t,u'}}} \ \ (u \le t), \qquad a_{t,u} = 0\ \ (u > t)\end{aligned}$$

Per head the score table is \([5,\,5]\); across the 16 heads it is \([16,\,5,\,5]\). Computing it costs \(2 \times 5 \times 5 \times 128 = 6{,}400\) operations per head, a rounding error beside the projections. It grows with the square of the prompt length, which is why long prompts are expensive.

Mixing values, merging heads

The attention weights now pick what to read. Each token's new vector, per head, is the weighted sum of the value vectors of the tokens it attends to. The 16 head outputs, each 128 wide, are placed side by side into 2048 numbers per token, and one more learned matrix \(W_O\) maps 2048 back to 1024, so the result can be added to the residual. For ‘ is’ the first output feature is -0.535. Added to the token's own 0.0183 it gives -0.517. That is the end of the attention half of the layer.

Each head hands the token a short briefing assembled from the packages of the tokens it paid attention to. The output matrix is the editor who merges 16 briefings into one note in the notebook's own format.

$$O_h = A_h V_{\operatorname{kv}(h)} \in \mathbb{R}^{[5,\,128]},\qquad h' = h + \big[O_0 \,\|\, \cdots \,\|\, O_{15}\big]\, W_O,\qquad [\,\cdot\,] \in \mathbb{R}^{[5,\,2048]},\ W_O \in \mathbb{R}^{[2048,\,1024]}$$

The output matrix has 2,097,152 weights and costs \(2 \times 5 \times 2{,}097{,}152 \approx 21\) million operations. Weighted sums add only \(2 \times 5 \times 5 \times 128\) per head, again tiny. Note which key/value head each query head reads: \(V_{\operatorname{kv}(h)}\), the shared one.

The feed-forward network

Attention moved information between tokens. The second half of the layer works on each token alone, with no exchange. It starts with a second RMSNorm (for ‘ is’ the mean of squares is 0.0307), then three matrices. The gate and up projections each widen the vector from 1024 to 3072. The gate is passed through SiLU, a smooth curve that is near zero for negative inputs and near the identity for positive ones, and the result multiplies the up projection feature by feature. The down projection narrows 3072 back to 1024. In the code it is a single line: down of SiLU of gate, times up.

For ‘ is’, the first gate value is -2.31 and the first up value 1.34. SiLU squashes the negative gate to -0.209, and the product is -0.279. After the down projection and the residual add, the layer's output for this feature is -0.853.

The gate decides, feature by feature, how much of each of 3072 candidate patterns to let through, and the up projection supplies the patterns. Many accounts say this is where much of a model's stored knowledge lives, which is an interpretation. The arithmetic itself is just gated, widened matrix multiplies.

$$\operatorname{FFN}(x) = \Big(\operatorname{SiLU}(x W_{\text{gate}}) \odot (x W_{\text{up}})\Big) W_{\text{down}},\qquad \operatorname{SiLU}(z) = \frac{z}{1 + e^{-z}}$$

Shapes: \(x \in \mathbb{R}^{[5,\,1024]}\), the two widened tensors \([5,\,3072]\), the output \([5,\,1024]\). The three matrices have \(3 \times 1024 \times 3072 = 9{,}437{,}184\) weights, 60% of a layer, and cost \(2 \times 5 \times 9{,}437{,}184 \approx 94\) million operations for the five tokens. This block, not attention, dominates the arithmetic of a short prompt.

The feed-forward block: ReLU, gates, experts

The Transformer’s feed-forward network was plain: two linear transformations with a ReLU activation in between, with a model width of 512 and an inner layer of width 2048, four times wider than the model. At that shape a layer holds two matrices of size d by 4d, so eight d squared weights, which for our width is 8,388,608.

Two changes followed. The activation got smoother: Hendrycks and Gimpel (2016) proposed the Gaussian Error Linear Unit (GELU), a high-performing neural network activation function. Then came gating, a second projection that decides how much of each feature passes. Dauphin and colleagues (2016) proposed a novel simplified gating mechanism for language modelling, which Shazeer (2020) cites as Gated Linear Units. Shazeer tested variants inside the Transformer and found that some of them yield quality improvements over the typically-used ReLU or GELU activations. A gate adds a third matrix, so to keep the number of parameters and the amount of computation constant, we reduce the number of hidden units by a factor of two thirds. LLaMA replaces the ReLU non-linearity by the SwiGLU activation function with a dimension of two thirds of four d instead of four d.

Qwen3-0.6B uses SwiGLU with width 3,072, three times the model width, a little above the two-thirds rule, which would give 2,730. Its layers hold 9,437,184 feed-forward weights, against 8,386,560 at the rule and 8,388,608 for the ReLU shape.

A different direction raises the parameters without raising the work per token. Shazeer and colleagues (2017) report a sparsely-gated mixture of experts with more than a thousandfold improvement in model capacity with only minor losses in computational efficiency. Switch Transformers simplify the MoE routing algorithm, and in Mixtral a router network selects two experts to process the current state, so each token has access to 47 billion parameters, but only uses 13 billion active parameters during inference. Qwen3-0.6B is dense: the mixture row in the table is a what-if with eight experts and two used, copying Mixtral’s shape at our sizes.

What the choices cost on our model: a ReLU block does about 16.8 million operations per token and the SwiGLU block about 18.9 million, since each weight takes one multiply and one add. The mixture stores 75,497,472 weights per layer, eight times a dense block, but a token uses only 18,874,368 of them plus a tiny router, about 37.8 million operations for two experts. For memory, a decode step reads the active weights: 18.9 MB of the dense block in BF16, or about 37.7 MB for the two chosen experts, though the whole 151 MB per layer must still be held somewhere. The KV cache does not change at all: the feed-forward network keeps nothing per token.

A ReLU block is a bank of 4,096 switches, each turning on when its pattern appears in the vector. SwiGLU makes each switch a dimmer: one projection, the gate, says how much, and another, the up projection, says what. A mixture of experts replaces the one big bank with a hall of eight specialist banks and a receptionist, the router, who sends each token to two of them.

That was layer 0. The next 27 do the same work with their own weights. Because every layer only adds to the residual, we can peek at the vector between layers. The last vector becomes 151,936 scores

One table or two: tying the embeddings

The input embedding table turns an ID into a vector, and the output layer turns the last vector back into one score per vocabulary entry. Early language models gave each job its own matrix. Press and Wolf (2016) recommended tying them; their methods led to a significant reduction in perplexity, and weight tying can reduce the size of neural translation models to less than half.

For a small model the saving is large. Our table has 151,936 rows of 1,024 numbers, 155,582,464 parameters, which is 26.1% of this model’s 596,049,920. Untied, the model would carry a second table of the same size: 311,164,928 embedding parameters, 751,632,384 in all. In BF16 that is 311,164,928 bytes tied and 622,329,856 untied. Qwen3-0.6B ties them.

Tying saves storage but not reading. The lookup reads one row of the table. The output layer reads the whole table once per decode step, about 311 MB of the 1.19 GB of weights, whether or not it is shared. The KV cache is untouched.

One dictionary used in both directions: to read a word, look up its meaning vector; to write a word, find the entry whose meaning vector best matches what the model has in mind. Keeping one dictionary keeps the two directions consistent, and in a small model it frees a quarter of the weights for the layers that do the thinking.

Prefill by the numbers

Here is the bill for reading the five-token prompt. The model has 596,049,920 weights, 155,582,464 of them the tied embedding table. For the five tokens, one layer's attention projections cost 62.9 million operations and its feed-forward network 94.4 million, the score and mixing steps 0.2 million. Over 28 layers that is 4.41 billion, and the head adds 0.31 billion for the last token: about 4.7 billion operations. Reading every weight once costs 1.19 billion bytes at 2 bytes each.

What that means: five tokens' worth of work uses each weight five times, so the arithmetic per byte moved is about 4. A long prompt of thousands of tokens uses each weight thousands of times, which is why prefill tends to be limited by compute, while the single-token decode that follows is not.

Reading a long page aloud versus checking one word. Prefill amortises the cost of fetching the weights over every token of the prompt. Decode pays the full fetch for a single token.

$$\text{FLOPs} \approx 28\Big(\underbrace{2\!\cdot\!5\!\cdot\!6.29\text{M}}_{\text{attention matrices}} + \underbrace{2\!\cdot\!5\!\cdot\!9.44\text{M}}_{\text{feed-forward}} + \underbrace{0.2\text{M}}_{\text{scores, mix}}\Big) + \underbrace{2\!\cdot\!1024\!\cdot\!151936}_{\text{head, last row}} \approx 4.7\times 10^{9}$$

Activations stay \([5,\,1024]\) between sublayers and \([5,\,3072]\) inside the feed-forward. All of these counts come from the config and are recomputed by our tests. The arithmetic intensity, operations per byte of weights read, is \(4.7\text{G} / 1.19\text{G} \approx 4\) for five tokens.

What prefill leaves behind: the KV cache

During prefill, every layer computed keys and values for the five tokens. Those will be needed again at every later step, and they never change: a token's keys and values depend only on itself and the tokens before it, and the mask guarantees that. So instead of recomputing them, each layer appends them to a cache. What is stored is the keys after the normalisation and rotation (we checked that the model's own cached keys equal ours), and the values as projected.

The cache of one layer holds \(8 \times 5 \times 128\) keys and the same number of values: shape \([8,\,5,\,128]\) each. In BF16 that is 4,096 bytes per token per layer, and across 28 layers 114,688 bytes per token, or 573,440 bytes for the five tokens. It is small now. It grows by one token's worth each step, and for a long conversation it can outgrow the weights.

A notebook of everything every earlier token ever offered to a question. Each new token writes one line in the notebook and reads all the others, instead of making the earlier tokens re-answer.

$$K_{\text{cache}},\,V_{\text{cache}} \in \mathbb{R}^{[8,\,T,\,128]},\qquad \text{bytes per token} = \underbrace{28}_{\text{layers}} \times \underbrace{2}_{K,V} \times \underbrace{8}_{\text{heads}} \times \underbrace{128}_{\text{dim}} \times \underbrace{2}_{\text{B}} = 114{,}688$$

The cache is per sequence, per layer and, with GQA, per key/value head, not per query head. That choice is what the GQA beat bought.

Decode: one new token

Now the model has written ‘ Paris’ (ID 12,095) and we want the word after it. The input to the model is only that one token, at position 5. Its embedding is one row, so every vector in the layer is one row instead of five. In each layer the new token computes its own query, key and value. Its key and value are appended to the cache, which now holds six positions, and its query is scored against all six keys, the five old ones read from memory and the new one just made.

That read is the whole point of the cache. For our layer-0 head 0, the new token's attention is 13.1% on ‘ The’, 66.7% on ‘ France’, 11.6% on ‘ is’ and 1.26% on itself. It looks back mostly at ‘ France’, which is plausible, though one head of one layer is thin evidence of what the model is doing. Another head, head 5, puts 100% on the new token alone. The cache was updated by the same line of code as in prefill, only with one row.

After 28 layers and the head, the next-token distribution is: ‘.’ at 42.9%, ‘,’ at 37.5%, then ‘ and’ at 6.78%. A sentence like this can end in a full stop or a comma, and the model puts nearly all its probability on those two.

The new word walks into a room where everyone has already said their piece and written it on the board. It reads the board, adds its own line, and the room's verdict is a prediction of the next word. No one has to repeat themselves.

$$\begin{aligned}&q_{\text{new}} \in \mathbb{R}^{[16,\,128]},\quad K_{\text{cache}} \in \mathbb{R}^{[8,\,6,\,128]} \\ &a_h = \operatorname{softmax}\!\Big(\tfrac{q_{\text{new},h}\,K_{\operatorname{kv}(h)}^{\top}}{\sqrt{128}}\Big) \in \mathbb{R}^{[6]},\qquad o_h = a_h V_{\operatorname{kv}(h)} \in \mathbb{R}^{128}\end{aligned}$$

We recompute head 0 in code from the recorded query and the six cached keys and obtain the same weights as the model. Position matters: the new key is rotated by position 5, the cached ones keep the rotations from prefill.

Why decode is slow: reading the weights

One row through a layer is a matrix-vector product, not a matrix-matrix product. The arithmetic for one token is about 1.19 billion operations, and to do it the processor must read every weight once: 596 million numbers at 2 bytes, 1.19 billion bytes. That is about one operation per byte. A modern chip can do tens to hundreds of operations in the time it takes to fetch one byte, so decode waits on memory, and its speed is set by memory bandwidth, not arithmetic.

Added to that is the cache. At six tokens it is 688,128 bytes, nothing. But it grows by 114,688 bytes with every token: at 4,096 tokens the cache read is 470 million bytes, 40% of the weights, and at 32,768 tokens it is 3.76 billion bytes, three times the weights. The cache is what makes long conversations expensive, and shrinking it is the motivation for the next beats.

Prefill reads the weights once and uses them for many tokens, like a printing press run. Decode starts the press for each single page. To be fast it would have to reread everything for one line, and the cost of reading dwarfs the cost of thinking.

$$\text{tokens/s} \;\lesssim\; \frac{\text{bandwidth}}{\underbrace{1.19\times 10^{9}}_{\text{weights, BF16}} \;+\; \underbrace{114{,}688 \times T}_{\text{KV cache read}}}\qquad\Big(\text{e.g. } \tfrac{500\ \text{GB/s}}{1.19\ \text{GB}} \approx 420\text{ at small } T\Big)$$

With one token the activations are \([1,\,1024]\). The 500 GB/s is an illustrative figure, not a measurement of any machine in this study. The cache term is linear in context length \(T\), and the weights term is fixed. Decode reads what prefill left behind, and every weight again.

What grouped-query attention buys

The cache stores keys and values per key/value head, so the number of those heads sets its size. With one pair per query head (multi-head attention), the cache would hold 16 heads of 128, 8,192 bytes per token per layer. Qwen3's grouping to 8 halves it, 4,096. The extreme, one shared head for every query head (multi-query attention), would be 512. Grouped-query attention, introduced by Ainslie and colleagues in GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints, is a generalisation of multi-query attention with an intermediate number of key-value heads.

Across the model, at a 32,768-token context, that is 7.5 GB of cache for multi-head attention, 3.76 GB for GQA as built, and 0.47 GB for multi-query attention. The cost of sharing is expressiveness: fewer key/value heads means fewer distinct things each layer can look up, and designers choose the group size by balancing quality against memory.

Hiring fewer librarians. Each librarian serves more readers, the building is smaller, and the question is whether readers still get what they need.

$$\text{bytes}/\text{token}/\text{layer} = 2 \times n_{kv} \times 128 \times 2 = \begin{cases} 8192 & n_{kv} = 16\ \text{(MHA)} \\ 4096 & n_{kv} = 8\ \text{(GQA, Qwen3)} \\ 512 & n_{kv} = 1\ \text{(MQA)} \end{cases}$$

The cache of one layer is \([n_{kv},\,T,\,128]\) for keys and for values. Multiply by 28 layers and by the context length for the whole cache: \(114{,}688 \times 32{,}768 = 3{,}758{,}096{,}384\) bytes for GQA.

Multi-head latent attention

GQA shrinks the cache by sharing heads. Multi-head latent attention, MLA, takes a different route. The DeepSeek-V2 paper (arXiv 2405.04434) states that MLA compresses the key-value cache into a latent vector. Instead of caching every head's key and value, a layer caches one small latent vector per token and rebuilds the keys and values from it when needed.

We ran the real attention of layer 0 of DeepSeek-V2-Lite on the same sentence. (Its tokenizer gives the same five word pieces with different IDs, ‘ France’ being 7,239, and the model expects a start-of-sequence token in front, so we run six tokens.) Its hidden size is 2048 and it has 16 heads. One matrix maps each token's 2048 numbers to 512 + 64 = 576: a down-projection produces the 512-number latent, which is normalised (the latent for ‘ is’ has length 1.83), and a separate 64-number key that carries position. Only these two are stored. In the model's code, the cache is read and written while the latent is still compressed. When attention needs keys and values, one up-projection expands the latent: 512 numbers become, for each of the 16 heads, a 128-wide key and a 128-wide value.

The bytes tell the story. Per token and layer the cache holds \((512 + 64) \times 2 = \) 1,152 bytes, where caching full multi-head keys and values would take 10,240: 8.89 times smaller. The paper reports that DeepSeek-V2 reduces the KV cache by 93.3%, a figure for the full model against the baseline the paper names.

Instead of keeping a photocopy of every page for every reader, keep one compressed summary of the page, and let each reader rebuild their own copy from it on demand. The rebuild costs arithmetic, which a chip has plenty of, in exchange for memory traffic, which it lacks.

$$\begin{aligned}c &= \operatorname{RMSNorm}(x\,W_{DKV}) \in \mathbb{R}^{[T,\,512]} \\ k^{\text{nope}}_h &= c\,W^{UK}_h,\quad v_h = c\,W^{UV}_h \in \mathbb{R}^{[T,\,128]} \\ k^{\text{rope}} &= \operatorname{RoPE}(x\,W_{KR}) \in \mathbb{R}^{[T,\,64]}\end{aligned}$$

The score for head \(h\) adds two parts, \(q_h^{\text{nope}} \cdot k_h^{\text{nope}} + q_h^{\text{rope}} \cdot k^{\text{rope}}\), and multiplies the sum by a softmax scale of 0.1147 (it combines \(1/\sqrt{192}\) with the model's long-context rescaling). The rotary part is kept separate and shared across heads (decoupled RoPE), and only it is rotated. The query is 192 wide per head, a 128-wide content part and a 64-wide position part. The cache is \([T,\,512]\) plus \([T,\,64]\), per layer, not keys of \([T,\,16,\,192]\) plus values of \([T,\,16,\,128]\), which is 320 numbers per head.

Never rebuilding the keys

Rebuilding every head's keys from the latent at every step would be wasteful. MLA has a trick for decode. The content score is a chain of two matrix products, \(q^{\text{nope}} \cdot (c\,W^{UK})\), and matrix products can be regrouped: \((q^{\text{nope}} W^{UKT}) \cdot c\). So multiply the query by the up-projection once, getting a 512-wide absorbed query, and score it directly against the cached latents. The keys are never materialised. As the DeepSeek paper explains, this is why the position-carrying part is kept separate: a rotation that depends on position would sit between the matrices and block the regrouping.

We checked it on the real layer. The scene shows the 6×6 scores computed both ways for head 0, and they agree: the largest difference is 2.63 × 10⁻⁷, rounding error, and the attention weights match the model's own to the same precision. For ‘ is’ the weights over the six tokens (the start token first) are 23.8%, 18.1%, 4.24%, 24.9%, 9.34% and 19.6%.

Translating a question into the answer's language once, instead of translating every answer into the question's language. With one question and thousands of cached answers, that is the cheaper side to translate.

$$\begin{aligned}s_{t,u} &= \Big(\underbrace{q^{\text{nope}}_t W^{UK\top}_h}_{\in\,\mathbb{R}^{512}}\Big)\!\cdot c_u \;+\; q^{\text{rope}}_t \!\cdot k^{\text{rope}}_u \\ o_h &= \Big(\sum_u a_{t,u}\, c_u\Big) W^{UV}_h\end{aligned}$$

The absorbed query and the cached latents are both \([6,\,512]\). The value side regroups the same way: take the attention-weighted sum of latents first (a 512-vector per head) and apply \(W^{UV}_h\) afterwards. Each score now costs a 512-wide dot product instead of a 128-wide one, more arithmetic per step but no rebuild and, more important, a cache read of 1,152 bytes per token instead of 10,240.

From MHA to MLA: shrinking attention’s memory

The first Transformer used eight parallel attention layers, or heads so that the model could jointly attend to information from different representation subspaces. Each head has its own queries, keys and values, so every token leaves, in the cache of every layer, one key and one value for each head. With our 16 heads of 128 numbers, in BF16, that is 8,192 bytes per token per layer.

Decoding reads the whole cache for every new token, and Shazeer (2019) named the reason decoding is slow: the memory-bandwidth cost of repeatedly loading the large “keys” and “values” tensors. His fix, multi-query attention, makes the keys and values shared across all of the different attention heads. One key/value head means 512 bytes per token per layer, sixteen times smaller.

One shared head costs quality, so Ainslie and colleagues (2023) took the middle road with grouped-query attention: an intermediate (more than one, less than number of query heads) number of key-value heads, with quality close to multi-head attention with comparable speed to MQA. They made it cheap to adopt: each group key and value head is built by mean-pooling all the original heads within that group, and their recipe for uptraining a multi-head checkpoint used 5% of original pre-training compute. Mistral 7B leverages grouped-query attention (GQA) for faster inference. Qwen3 uses 8 key/value heads for 16 query heads, 4,096 bytes per token per layer.

Multi-head latent attention goes a different way: not fewer heads, but a smaller thing to store. DeepSeek-V2 (2024) describes significantly compressing the Key-Value (KV) cache into a latent vector. Compared with DeepSeek 67B, the paper reports that the DeepSeek-V2 model reduces the KV cache by 93.3%, and boosts the maximum generation throughput to 5.76 times; that is the whole model against its predecessor, not our comparison. The paper describes the MLA cache as equal to GQA with only 2.25 groups, but its performance is stronger than MHA. In our recorded run of DeepSeek-V2-Lite’s first layer the cache is 1,152 bytes per token per layer against 10,240 for full multi-head keys and values, about 8.9 times smaller.

Two neighbours attack the other factors, the number of tokens and the traffic of the scores. Sliding-window attention limits how far back a token looks: Longformer combines a local windowed attention with a task motivated global attention, and Mistral 7B uses sliding window attention (SWA) to effectively handle sequences of arbitrary length with a reduced inference cost. FlashAttention changes how scores are computed, not what is cached: it uses tiling to reduce the number of memory reads and writes between GPU high bandwidth memory and on-chip SRAM.

Picture each head as an analyst who files an index card, a key and a value, for every sentence read. In multi-head attention all sixteen analysts keep private card files. Multi-query gives them one shared file: tiny, but everyone reads the same cards. Grouped-query gives eight files, shared by pairs. Latent attention stops filing the cards at all: it files one compressed note per sentence and lets each analyst expand it when needed.

Each layer caches \([n_{kv},\,T,\,128]\) for keys and for values. The multi-head count matches the paper’s: multi-head attention needs to cache two times the number of heads times the head size, per layer, for each token. For Qwen3, \(n_h=16\), \(n_g=8\), \(d_h=128\), \(b=2\), which gives 8,192, 4,096 and 512 bytes per layer. Over 28 layers and the five tokens of our prompt that is 1,146,880, 573,440 and 71,680 bytes. Sharing keys and values leaves the arithmetic of attention untouched and cuts the bytes it must read, which is exactly the resource that limits decoding. Parameters change too. The key and value projections hold 4,194,304, 2,097,152 and 262,144 weights per layer, so the whole attention block holds 8,388,608, 6,291,456 and 4,456,448. Going from 16 to 8 key/value heads saves 58,720,256 weights over 28 layers, about 9.9% of the model. In the five-token prefill the key and value projections of GQA take 587,202,560 operations. These are what-if sizes at fixed width; in published comparisons the models are retrained, so quality differences come from training and not from this arithmetic.

Other new features you will meet

Qwen3-0.6B stops here. Newer models add more, and this article's pieces are the base they build on. Sliding-window attention limits each token to the last few thousand, so the cache stops growing for those layers. Mixture of experts replaces the single feed-forward network with many, of which a router picks a few per token, so a model can store far more than it computes with. Attention residuals replace the plain running sum with a learned mix over earlier blocks. The whole picture

The five tokens became IDs, the IDs became vectors, and each of 28 layers added two corrections to every vector. The first came from attention: normalise, project to 16 queries and 8 shared keys and values, normalise the queries and keys, rotate them by position, score, mask, softmax, mix, merge the heads. The second came from the feed-forward network: normalise, widen to 3072 twice, gate with SiLU, narrow back. After the stack, the last vector was normalised and dotted with the 151,936 rows of the embedding table to give logits, softmax gave probabilities, and the vocabulary turned the winning ID into ‘ Paris’. The cache kept the keys and values, so the next token cost one row, not six.

Everything in a transformer is the same four moves repeated: normalise, multiply by a learned matrix, mix with weights that depend on the data, and add the result back. What changes between designs is how many heads there are, how they share, and what is cached.

$$\underbrace{[5]}_{\text{ids}} \to \underbrace{[5,1024]}_{h_0} \to \underbrace{[5,2048],\,[5,1024]^2}_{Q,\,K,\,V} \to \underbrace{[16,5,5]}_{\text{weights}} \to \underbrace{[5,1024]}_{\text{attn out}} \to \underbrace{[5,3072]^2}_{\text{gate, up}} \to \underbrace{[5,1024]}_{h_{28}} \to \underbrace{[151936]}_{\text{logits}} \to \text{“ Paris”}$$
